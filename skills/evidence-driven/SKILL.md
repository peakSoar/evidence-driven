# 证据驱动工程 Harness

将工程任务组织为“事实 → 计划 → 实施 → 验证 → 状态与接力”。

## Python 解释器检查

首次运行本技能的 Python 脚本前，按顺序检查用户已有的解释器：

```text
python -c "import sys; print(sys.executable)"
python3 -c "import sys; print(sys.executable)"
```

使用第一条成功返回的解释器绝对路径，第一条失败时再检查第二条。不额外检查版本

将路径保存为当前终端临时变量 `PYTHON_EXECUTABLE`，后续脚本统一使用该路径；新终端中重新设置已确认的路径。

两条命令均失败时回复 **没有python依赖**，继续阅读、规划和文档审计；脚本运行等待用户提供可用解释器。

## 先恢复，再决定范围

遵循用户指令和目标仓库的有效规则，以源码、测试和本轮运行证据校正文档与聊天摘要，保留项目已有技术边界与用户修改。不机械覆盖，遇到Harness章节冲突、变动，停止编辑，与用户核对。

按项目恢复顺序读取；没有约定时使用：仓库指令 → 计划与唯一状态 → 当前接力 → 当前阶段合同 → 合同引用的源码、测试和验证条目；按需读取当前验收与历史。核对 HEAD、分支和工作区。

恢复后简述本阶段目标、已验证与未验证事项、关键边界和第一步行动。影响实施的歧义或重大业务取舍交由用户确认，其余按已有授权继续。

先选模式：建立或整理工作流用“初始化/转换”；按已有流程做任务用“执行”；检查一致性用“审计”。局部、低风险、单会话任务不创建阶段；跨会话、跨模块、重要边界变更或需要发布及人工操作时才考虑阶段化。

阶段化按任务规模决定，已建立的 Harness 文档按完整结构维护。

## 文档职责

沿用目标仓库等价文件；新建时使用 `assets/harness-template/` 下的模板：

| 文件 | 唯一职责 |
| --- | --- |
| `AGENTS.md` | 长期边界、owner、恢复入口、权限和工作区规则 |
| `docs/改造计划与进度.md` | 问题基线、依赖、唯一当前阶段及重开状态 |
| `docs/当前阶段与下一步.md` | 最近继续点与下一会话提示 |
| `docs/阶段/Sxx-*.md` | 本阶段目标、允许范围、方案和退出条件 |
| `docs/验证规则.md` | 复用验证口径与反馈规则 |
| `docs/验收/当前验收.md` | 最近一轮实际执行证据，每轮整体覆盖 |

保留模板章节，按其中的填写提示结合仓库事实生成正文，完成后移除填写提示与占位符。不适用的章节保留标题并说明原因。阶段第 4 节可按业务问题增加子标题。

阶段合同记录计划，当前验收记录本轮事实与偏差，每轮整体覆盖；历史统一由 Git 保存。覆盖前核对旧验收中仍需引用的证据是否已保存；存在未提交且将丢失的必要证据时，说明保存缺口，按用户的版本保存安排处理后再覆盖。

接力使用摘要与指针，列明下一步动作、前置条件和未验证事项；详细事实保留在阶段合同、当前验收或明确的 Git 版本中。

## 生成完整结构（默认路径）

初始化/转换模式默认产出完整结构。

1. 检查项目指令、架构、模块 owner、数据保留、契约源、资源与并发、敏感信息、验证入口、Git 状态和外部操作边界，区分已有事实与目标设计。

2. 阅读六份模板和 `assets/examples/fill-samples.md`，确认各章节对应的项目事实。

3. 用临时变量中的解释器运行生成器，把完整结构落到目标仓库：

   powershell:

   ~~~powershell
   & $PYTHON_EXECUTABLE scripts/scaffold_harness.py --target <目标仓库> --project-name <项目名称> --dry-run
   ~~~

   bash/zsh:

   ~~~bash
   "$PYTHON_EXECUTABLE" scripts/scaffold_harness.py --target <目标仓库> --project-name <项目名称> --dry-run
   ~~~

4. 核对预览后去掉 `--dry-run` 执行生成。遇已有文件时保留原文件，核对后用 `--keep-existing` 补齐缺项，在已有授权内继续。

5. 已有等价文档时，在原位置对照模板补齐章节。

6. 按填写标准完成正文，将未确认事项标为证据缺口，然后执行交付断言。

### 精简模式（仅在用户明确要求时）

用户明确要求最简或轻量结构时，先生成完整结构再裁剪，在《当前验收》中记录裁掉的文件、章节和理由，保留章节仍按填写标准完成。

## 章节结构偏差时生成骨架

用户反馈章节或目录结构不对，或要求恢复模板章节时，调用 `scripts/generate_headings.py`。脚本从现有模板提取标题及各级子标题，不生成正文，不自动迁移旧内容。

先按前述规则确认 Python 解释器。以下路径相对于技能目录；默认只输出到终端：

```powershell
& $PYTHON_EXECUTABLE scripts/generate_headings.py --document acceptance --project-name <项目名称>
& $PYTHON_EXECUTABLE scripts/generate_headings.py --document stage --title 'S07 借阅续借与归还'
```

`--document` 可选：`agents`（项目指南）、`plan`（计划与进度）、`handoff`（当前阶段与下一步）、`verification`（验证规则）、`stage`（阶段合同）、`acceptance`（当前验收）。Bash/zsh 使用 `"$PYTHON_EXECUTABLE"` 调用同一脚本和参数。

加 `--output <新文件路径>` 可保存骨架，父目录须已存在，已有目标文件会触发失败。以骨架和原模板的填写提示为依据，在原权威文档中整理正文，保留有效业务内容与证据，替换项目名和阶段号，最后执行交付断言。

## 填写标准

占位符和正文都要写成可判定的事实。一条合格的填写同时具备三项：

- **主语**：谁拥有、哪个模块、哪个类、哪个角色。
- **位置**：文件、类、方法、行号、端口、键名、表名、命令中的至少一项。
- **可观察结果**：能被运行或检查的东西——退出码、状态码、字段值、行数、键的 TTL、某个方法的返回值。

写清具体动作、位置与结果，参考 `assets/examples/fill-samples.md`。未确认的内容写“证据缺口：<事实>，需要 <动作或数据> 才能确认”；影响设计的假设标记为 `HYPOTHESIS` 并给出验证方式。暂时无法填写的章节保留标题，写“待定：<缺什么>”，同步记入验收的未运行项。

## 执行

1. 冻结 HEAD、分支、预存修改、允许范围、事实、证据缺口和验证计划。真实系统任务按需记录运行版本、配置标识和数据水位，保护敏感信息。
2. 追踪 producer（产生数据）、transition（转换数据）、consumer（消费并决策）和唯一 owner；区分代码原因、数据现象和环境失败。发现旧测试固化错误时先说明契约。
   涉及接口、数据库、权限或状态边界时，核实现状，在阶段设计中写清目标契约、影响和待决策事项，完成必要确认后实施。
3. 行为修改先建立 characterization（当前行为）和目标失败测试（违反的契约），使用中性 fixture。纯文档、注释和无行为机械改动可免红灯；项目允许的其他例外记录理由。
4. 复杂阶段按依赖与风险拆成可独立验证的批次，明确每批产物、验证方式和完成条件，逐批最小实现并验证后继续。执行定向测试、受影响回归和必要门禁，全量测试、构建和真实验收按项目要求与风险选择。
5. 每项失败记录根因、责任归属和下一步；不能删除断言、篡改样例、跳过失败、硬编码业务样例或修补真实数据来制造通过。
6. 必要人工动作前完成已授权准备，列出目标、版本、水位及“操作步骤 → 预期结果 → 异常检查入口”。用户完成后按提供的 ID 或事前水位只读验收本轮产物，记录逐项结论与遗留项。
7. 整体更新当前验收，再回写状态与接力。普通任务不改已完成阶段状态；继续后续工作须在用户授权范围内。

## 证据、结果与状态

关键结论标记证据等级：
- `CONFIRMED`：多类证据交叉一致。
- `CODE_CONFIRMED`：源码或测试直接确认。
- `DATA_CONFIRMED`：本轮运行或数据直接确认。
- `STRONG_INFERENCE`：有支持但缺直接闭环，只驱动可逆验证。
- `HYPOTHESIS`：待核验，只用于调查。

检查结果按实际情况记录为通过、失败或未运行。失败说明影响、原因和下一步；环境阻塞与代码问题分开说明。仅有改进建议时如实记录，不作为已发生故障。任务是否完成按目标仓库的退出条件和实际证据判断。

阶段状态只有一处维护：
- `NOT_STARTED → IN_PROGRESS → DONE`：退出条件和必要验收全部满足才能完成。
- 实现或回归失败保持 `IN_PROGRESS`。
- 已复现的环境或权限阻塞进入 `BLOCKED`，写明解除条件。
- 需要必要人工动作进入 `HUMAN_ACTION_REQUIRED`；完成后回到 `IN_PROGRESS` 验收。
- 新证据推翻已完成 owner 时 `DONE → REOPENED → IN_PROGRESS`，重开最早责任阶段，记录原状态、恢复点和后继基线；不得在后继阶段复制临时修复。
- 同时只有一个活动阶段或活动重开；遵循项目已有重开协议，已完成计划的新需求新建阶段或计划，不重置旧状态。

## 交付断言

生成、转换或整体更新文档后逐条核对，全部满足后报告完成，其余情况报告未满足项和下一步。

| 断言 | 检查方式 |
| --- | --- |
| 无遗留占位符 | `grep -rn "{{" <目标> --include=*.md` 零命中，保留的说明性占位符须在验收里点名 |
| 填写提示已清理 | 交付文档中的模板填写提示注释已移除 |
| 章节与模板一致 | `AGENTS.md` 与阶段、验收、验证规则文件的模板章节逐条对齐；阶段第 4 节允许增加业务子标题；缺失章节在验收写明理由和用户确认 |
| 接力五栏齐全 | 当前状态、最近完成、当前继续点、必须保留的边界、下一会话提示五栏都在 |
| 最近完成不超上限 | 每条带 `YYYY-MM-DD`；当天条目全留；总数不超过 5 条 |
| 状态四处一致 | 计划正文、JSON 块、接力、当前验收中的阶段与状态完全相同，且只有一个活动阶段或活动重开 |
| 基线与退出条件可判定 | 问题基线每行有责任阶段，每个阶段有退出条件，条件是可以判断真假的事实而不是形容词 |
| 引用可解析 | 文档间相对链接指向真实文件，代码块成对闭合 |
| 范围未越界 | `git status --short` 的改动落在允许范围内，预存用户修改未被覆盖 |
| 敏感信息 | 验收不含密钥、凭据、Token、`Authorization`、真实密码与业务载荷 |

## 审计

审计时对照状态、合同、接力、当前验收、源码和测试，检查重复权威、重复 owner、旧验证结论、未处理失败、权限扩大、失效链接和敏感内容。仅要求审计时报告问题，不改文件。

当前验收的记录项按模板逐节填写，实际命令、时间、退出码、测试数量和真实操作证据均对应本轮执行。

提交、推送及其他外部操作遵循用户授权。
